# 碎片拼贴根源是数据污染（zhuangxialie 任务碎片占 train 55%）

## 背景（为什么做）

方向 1（生成自蒸馏 EI）冒烟：想用 af checkpoint 高温度采样一批"好对话"做蒸馏数据。
结果采样全崩成**文字拼贴**（对对联/实体识别/网易云热评/翻译题等任务模板碎片 + 中英文乱码混搭），
一条像样的对话都没有 → EI 教师无料可教。这不是脚本 bug——排查后定位到数据。

## 现象 → 排查链

1. T=1.1 崩 → 对齐 sample_py 参数 T=0.8 仍崩 → 长 prompt 崩、短 prompt（"你好"）也崩
2. 一度怀疑 `sample_py.py` 没 `.eval()`（dropout=0.2 开着）——但 `build_model_from_checkpoint`
   里已有 `model.eval()`（inference/scripts/sample_py.py:39），排除 dropout 因素
3. `inference/sample.py`（权威采样器，同样 eval）采 af **同样碎片拼贴** → 排除采样路径，是模型真实状态
4. checkpoint 元数据正确（iter 1500, val 1.0867, af 架构）→ 排除加载问题
5. 拼贴内容是任务模板碎片 → 查训练数据 → **zhuangxialie_dialogue.txt（149MB 单轮指令）占 train 54.7%**

## 根因

train 数据构成（2026-08-11 扩充后）：
- zhuangxialie（单轮指令：对对联/实体识别/摘要/热评/自然语言推理）149MB = **54.7%**
- multi_turn（对话）133MB × 0.9 = 43.8%
- dailychat/muice/shareai ≈ 1.5%

prepare.py 把非对话文件**全部进 train**（"让模型学全面"），导致 train 里一半以上是任务碎片。
模型自由生成时的先验 = "接碎片"（因为 55% 训练信号是碎片）。val 只看对话（prepare.py 设计），
所以 **val 1.0867 很低但采样崩**——又一个"loss 骗低"实例，根源在数据分布不是拓扑/目标。

这也推翻 dev-notes/18/19/20 里"af 绕圈但保持对话框架"的记录：当时是**相对对比**
（B2 更跳、mem 崩得更彻底），绝对质量其实都是碎片拼贴，只是没有用权威采样器复验。

## 修复

- `prepare.py` 加 `--task-ratio`（非对话样本保留比例，默认 1.0=现状）：
  - `--task-ratio=0` 剔除任务碎片，train 只剩对话
  - 每文件独立 seed（`1337 + sum(ord(c) for c in fn)`）保证可复现
- 重跑后 train 30.0M token（原 72.4M），94,097 对话条进 train / 10,457 进 val（仅对话）
- 原数据备份：`train.bin.bak-20260812-zhuangxialie` / `val.bin.bak-20260812`
- 用纯对话数据重训 af5k（out/chinese-data2-clean-af5k），采样验证碎片是否消除

## 怎么避免

- **采样崩先查数据分布，别急着改拓扑/目标**。三连崩坏（Sinks 死循环 / Muon 乱码 / 记忆拼贴）
  之后这次是"数据污染拼贴"——先确认 train 数据构成符合任务目标，再谈网络。
- 后续加语料时量化各文件 token 占比（不要只看文件个数），对话类/任务类分开配比。
- 排查陷阱：怀疑采样器 bug 时先确认 `build_model_from_checkpoint` 是否 eval()（本案例里
  它是 eval 的，无 dropout 问题）；用 `inference/sample.py` 做交叉验证最可靠。
- 数据治理后若 af5k 采样连贯，方向 1（EI）教师才成立；否则"小模型 + 纯对话"本身
  是否够"智能"是下一个问题。
