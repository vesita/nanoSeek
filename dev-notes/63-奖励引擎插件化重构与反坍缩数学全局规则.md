# 63-奖励引擎插件化重构与反坍缩数学全局规则

日期 2026-09-03
涉及: `training/rl/sampler.py` / `training/rl/updater.py` / `training/rl/reward/*` / `grpo_char.py`

## 背景与动机
旧 `multi_reward.py` 把所有奖励维度写死在单个 `evaluate_reply` 巨方法里：加一个维度
就得改几百行、维度之间靠共享局部变量 (`char_len`/`body`/...) 隐式耦合，且 RL 主管线
`grpo_char.py` 里采样/评估/优势合成三层混在一起。

本会话把奖励体系重构成**三维独立可组合模块 + 维度插件引擎**：

| 模块 | 职责 |
|---|---|
| `training/rl/sampler.py` | 采样候选 (temperature/top-k/repeat_penalty + 终止符) + token logprobs 提取 + 静默能量 + 奖励塑形分派 |
| `training/rl/reward/*` | 维度插件式奖励引擎 (注册 + 加权合成 RewardVector) |
| `training/rl/updater.py` | GRPO 优势合成 (优势归一化/winsorize/退化门控 + KL + 静默) |

## 奖励引擎 (维度插件式)
- `reward/base.py`: `EvalContext` = 一次评估的**全部只读输入快照** (冻结 dataclass, 含
  预计算的 char_len/body/han_ratio/term_kind/arith/first_digit/extra_digits/enum_run_len)；
  `RewardVector` = 10 维明细 + 加权合成；`RewardDimensionWeights` = 每维权重。
- 每个维度 = 独立纯函数 `fn(ctx) -> RewardVector` (只填自己负责的字段)；引擎
  `reward/engine.py` 按 `REGISTRY` 顺序逐个执行并求和 → 加权 total → 指数塑形。
- **新增维度只需写一个纯函数 + 在 `REGISTRY` 注册**，不碰其他维度。
- 兼容性: `MultiDimensionalRewardEngine = RewardEngine` 别名 + `_ngram_set` 转发，
  `dual_chat_selfplay.py` / `memory_rl.py` / `grpo_char.py` 的既有调用全部保持可用。

## 反坍缩修正 (r_anti_collapse)
本会话前的实测坍缩根因: `reward` 里 `hit_cont & should_cont → +1.2` 是**无条件正收益**，
模型发现只要"内容 + 吗/呢?"就能稳定刷 +1.2 → 全组退化成 5~12 字空递回残句
("是什么吗?""你们能试着这样呢?")，全组 eos=0/16 cont=16/16 空回复坍缩。

修正 (只让 cont 的 +1.2 在"言之有物且真需追问"时成立):
- 命中 `<cont>` 且正文极短 (<6 字) → **-2.5** (空递回主形态, 最严重)
- 命中 `<cont>` 且正文 6~15 字 (可疑) → **-1.0** (仍允许 r_control 部分正分, 别过度扣)
- 纯 `<cont>` 空回复 (L==0) → **-2.5**；另有 `r_fatal_empty` → **-3.5** 兜底
- 短收尾 (<4 且 `<eos>`) 由 r_natural **-2.5** 处理, 不叠加

## 数学题奖励 (全局规则 R1/R2)
`grpo_char.py` 提示词池新增 6 条数学 warm-start prompt (kind="arith", `--arith_ratio`):
3加4等于几? / 15减7等于多少? / 8乘3等于多少? / 24除以6等于几? / 12加9等于? / 20减13等于多少?

**R1 (数学题, 仅算式 prompt 生效)** — 回复按空格切分, **第一个数字 token** = 答案:
- 首数 == 算式正确结果 → 高分 **+2.5** (w_arith=1.5)
- 否则 (答错/没给首数字) → **-1.2**
- **多余数字** (首数之后、且不属于顺序列举) → 每个 **-0.8** (封顶 **-1.6**),
  惩罚往算式里掺杂质数字; 即使首数答对了, 掺了多余数字也扣。

**R2 (顺序列举豁免, 全局规则)** — 回复数字构成一段"+1 连续递增"列举 (长度>=3,
如 1 2 3 / 13 14 15, 由 `ordered_enum_run_len` 判定):
- 这些列举数字从"多余数字扣分"里**豁免**
- 并给少许 **+0.6** 奖励
- "列举作为全局奖励"= 不依赖算式, 一段干净的顺序列举本身就是可取文本形态

## GRPO 管线重构
- `grpo_char.py` 主循环: random.choice(pool) → `sample_candidates_batch` 采样 →
  逐候选算 raw score (含 mlp 基座似然门控) → exp 塑形 + div_weight ngram 多样性 →
  `GrpoUpdater.normalize_advantages` + winsorize → 退化门控 (组最高分<0 / 基座似然过低
  时把优势归零, 只留 KL/EOS 静默) → 逐候选提 logprobs + quiet → `updater.update_step`。
- 保持 v1 基线语义: 默认**纯优势加权** (`old_logprobs=None`, 无 importance ratio),
  browser 端不切换 PPO-clip。
- 关键修复 (本会话落地):
  - `HSA_OVERRIDE_GFX_VERSION=10.3.0` 为必需环境变量 (否则 HIP `invalid device function`)
  - logprobs 数组索引 i 对应 `full_ids[i+1]` → 回复位切片 `[prompt_len-1 : prompt_len-1+reply_len]`
  - 优势 tensor 显式 `.to(device)` 修复 cuda:0 与 cpu 混用; 空回复静默用 `device=device`
- 2-step GPU 冒烟通过: Loss 1.91, 组均分 9.70, eos=4/4 cont=0/4 均长 15.8,
  模型保存 `out/rl_cont_v2/best.pt`。
