# 76-稀疏分区字级词表v3与多源语料扩充实证

## 1. 背景与目标
在 nanoSeek 迈向 100M 参数规模的过程中，数据规模与分词器的可扩展性成为两大核心瓶颈：
1. **数据缺口**：治理后激活语料仅 ~45.8M tokens，距 100M 模型收敛底线（300M~500M）存在 10 倍级缺口；
2. **分词器刚性**：v2 三区词表把机制符与汉字紧贴排列，未来新增机制符（Agent/RL）或低频汉字会导致全局 id 错位。

本笔记记录**多源语料扩充**与**四区稀疏分区词表 v3**的设计与实证。

## 3. 四区稀疏分区词表 v3 设计（改良 v2）

### 3.1 分区布局
总词表 = **8192 = 2^13**（对齐硬件 GEMM 高效边界）：

| 区 | id 区间 | 容量 | 内容 | 稀疏预留 |
| :--- | :--- | :--- | :--- | :--- |
| 区1 基础字符 | 0~127 | 128 | 换行/空格/ASCII 32-126/全角标点 | ~11 位 |
| 区2 机制符 | 128~383 | 256 | `<eos>/<unk>/<cont>` + 9 个命名符 + 预留 | **244 位** |
| 区3 汉字 | 384~8191 | 7808 | 词频降序 top 6000 常用字 | **1808 位** |

### 3.2 关键机制符 id（固定语义，永不更改）
```
<eos>=128  <unk>=129  <cont>=130  <pad>=131  <bos>=132  <sep>=133
<call>=134  <result>=135  <think>=136  <answer>=137  <tool>=138  <search>=139
```

### 3.3 稀疏空间的核心价值
- **机制符扩展零错位**：未来 RL/Agent 新增 `<reward>/<observation>/<plan>` 等机制符，直接占区2 的 244 个预留位，汉字区 id 完全不动；
- **低频字无缝追加**：语料中出现新汉字时，追加到区3 尾部 1808 个稀疏位，旧 checkpoint 中已学汉字的 id 保持稳定；
- **对齐 2^13**：8192 词表让嵌入层与 LM Head 在硬件上享受对齐的 GEMM 加速。

## 4. 基础设施同步修复
1. **`eos_token_id` 配置化**：新增 `GPTConfig.eos_token_id`，修复此前 `is_eos = (idx == 0)` 把换行符误当 `<eos>` 的隐患；`train.py` 自动从 `char_tokenizer.json` 读取真实 `<eos>` id（v3=128）注入 config；
2. **训练数据编码**：`prepare.py` 的 `encode_to_bin` 采用动态 `token_to_id` 映射，对 id 迁移天然免疫，无需改动。

## 5. 结论
- 数据规模从 45.8M → **157.4M tokens**（3.4 倍），覆盖百科/逻辑/数学 CoT/代码/Agent 五大领域，初步补齐 100M 模型的通识与推理底座；
- 分词器升级为**四区稀疏分区 v3**，以 8192=2^13 对齐布局为未来机制符与低频字扩充预留了 **~2063 位稀疏空间**，彻底消除 id 错位风险；
- 模型架构（82M 参数）与 v3 词表接线验证通过，前向 loss 正常，可随时启动长程预训练。
