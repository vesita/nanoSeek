# 51-EOS数据修复与字符直入3500步验证

日期：2026-09-01  
模型：`out/eos_fix_1epoch` (2.70M 参数，6L + 因式分解嵌入 24d + KV记忆门控 + 8选2 MoE + 2-Step MTP)

---

## 1. 关键背景与根因定位

在上一轮字符直入 A/B 实验（Arm 0 基线 vs Arm 5 全要素 1500 步）中，模型展现出极高多样性（d1 0.876）与语法完整度，但对话出现两大异常：
1. **EOS 自吐率 0/10**（`stop_on_eos` 永不触发，强行填满 200 token）。
2. **话轮交替混乱**（模型输出完后自我扮演用户：`用户用户用户…`）。

### 根本原因
数据准备管线 `data/chinese/prepare.py` 中的 `encode_to_bin` 对字级 Tokenizer 采用朴素 `tokenizer.encode(chunk)`，导致：
- 字面量 `"<eos>"` 被逐字拆分为 5 个独立字符 token（`<`, `e`, `o`, `s`, `>`），**特殊 Token ID 0（`<eos>`）在 5280 万训练数据中出现 0 次**。
- 固定步长分块切割（`CHUNK=1M`）还会在块边界切断 `<eos>`，导致语料截断丢失。

---

## 2. 修复方案

1. **`prepare.py` 的 `encode_to_bin` 重构**：
   - 先按 `"<eos>"` 分割文本，各段独立编码，段间显式插入 Tokenizer 的 `eos_id`（ID 0），与 `encode_bytes_to_bin` 行为严格一致。
   - 重新生成 `train_char.bin`（140,674,897 tokens）与 `val_char.bin`（7,469,401 tokens）。
   - 验证：Token ID 0 出现 **1,193,055 次**，字面 5 字符 `<eos>` 残留 **0 次**。

2. **评测工具链修复**：
   - `health_check_hello.py` 修复硬编码 BPE 分词器导致字符直入模型 ID 越界崩溃的问题，自动对接 `load_tokenizer`。

---

训练配置：`batch_size=64`, `block_size=256`, `lr=1e-3`, `torch.compile=True`。  
训练在 3500 步（~0.41 epoch）因系统并发 Rust 编译触发 OOM 终止，但在 3500 步处完整保存了 `best.pt`（val loss 1.9021）。

- 用户：“我今天心情有点低落。” → 模型：“*那最让你你不用担心说乱，乱一点也没关系？*”
- 用户：“工作上遇到了点挫折。” → 模型：“*这部分挺清楚的 先把眼前这口气顺一顺也行——先从最有感觉的那块拿出来就行吗*”
- 用户：“感觉大家都不理解我。” → 模型：“*像是你能把它说出来——第二个失力的时候。脑子里对着的是哪件事呢？——嗯，这种时候人会特别想叹气。那种 咱可以一点点来*”
- 用户：“听你这么说我好多了。” → 模型：“*更像很多东西把自己劝住。你现在最不下子为什么难受，其实已经挺明白了*”

## 6. 结论

1. EOS 数据修复是使字符直入方案落地的最关键一环，彻底解决了自回归终止与角色越界问题。
2. 字符直入 + 因式分解嵌入使小模型（2.70M）彻底摆脱了 BPE 带来的“词块拼贴破碎”和“固定话术模板死锁”两大顽疾。
