# 51-EOS数据修复与字符直入3500步验证

日期：2026-09-01  
模型：`out/eos_fix_1epoch` (2.70M 参数，6L + 因式分解嵌入 24d + KV记忆门控 + 8选2 MoE + 2-Step MTP)

## 背景与根因
字符直入 A/B 实验（Arm 0 基线 vs Arm 5 全要素 1500 步）多样性极高（d1 0.876）、语法完整，但对话出现两大异常：
1. **EOS 自吐率 0/10**（`stop_on_eos` 永不触发，强行填满 200 token）。
2. **话轮交替混乱**（模型输出完后自我扮演用户：`用户用户用户…`）。

根因在 `data/chinese/prepare.py` 的 `encode_to_bin`：对字级 Tokenizer 用朴素 `tokenizer.encode(chunk)`，导致
- 字面量 `"<eos>"` 被逐字拆成 5 个字符 token，**特殊 Token ID 0（`<eos>`）在 5280 万训练数据中出现 0 次**；
- 固定步长分块切割（`CHUNK=1M`）在块边界切断 `<eos>`，语料截断丢失。

## 修复
1. **`encode_to_bin` 重构**：先按 `"<eos>"` 分割文本，各段独立编码，段间显式插入 Tokenizer 的 `eos_id`（ID 0），与 `encode_bytes_to_bin` 行为严格一致。
   - 重新生成 `train_char.bin`（140,674,897 tokens）与 `val_char.bin`（7,469,401 tokens）。
   - 验证：Token ID 0 出现 **1,193,055 次**，字面 5 字符 `<eos>` 残留 **0 次**。
2. **评测工具链修复**：`health_check_hello.py` 修复硬编码 BPE 分词器导致字符直入模型 ID 越界崩溃的问题，自动对接 `load_tokenizer`。

## 训练与效果评测（3500 步）
配置：`batch_size=64`, `block_size=256`, `lr=1e-3`, `torch.compile=True`。3500 步（~0.41 epoch）因系统并发 Rust 编译触发 OOM 终止，但在 3500 步处完整保存 `best.pt`（val loss 1.9021）。

### 实测文本
- 你好体检（固定开场 `用户：你好\n模型：`）：旧 Arm 5 喋喋不休 + 乱码自我扮演（强行占满 200 token）；新模型自然收敛（Seed 0/1 均 52 token 自动 EOS），呈心理支持共情口吻。
- 多轮心情场景 4 轮全部正常接话，无角色混淆。

## 网络内部激活状态
- 6 层死神经元率均 0.00%，无数值坍缩或爆炸（各层最大绝对值 0.67→3.50）。
- 最终 Train-Val Gap = 0.82（Train 2.72 vs Val 1.90，无过拟合）。

## 结论
1. EOS 数据修复是使字符直入方案落地的最关键一环，彻底解决了自回归终止与角色越界问题。
2. 字符直入 + 因式分解嵌入使小模型（2.70M）彻底摆脱 BPE 带来的「词块拼贴破碎」和「固定话术模板死锁」两大顽疾。
