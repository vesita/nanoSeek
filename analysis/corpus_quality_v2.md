## 1. 口径与方法

### 1.1 block 与"回复"的定义（两种口径必须分开）

严格对齐 `prepare.py`：

- `block = text.split('\n\n')` 后 `strip()` 非空的片段（`open(..., 'r')` 的 universal newlines 语义，见 §8.3）。
- **strict 口径**：`模型：` 行（strip 后以此开头）的 `：` 之后正文——**这正是 `annotate_replies` 实际标注的对象**。
- **span 口径**：该行 + 其后所有非 `用户：`/`模型：` 开头的续行——**这才是"回答"本身**。

两者在多数源上相同（回复本来就是单行）；但对多行回答的源差别巨大（§8.1），
所以本报告**两个口径都报**，12-gram 覆盖率统一用 **span**（"回答正文里有多少是套话"才有意义）。

### 1.2 两个不同的病症

| 指标 | 度量什么 | 典型病灶 |
|---|---|---|
| `rep3`（对齐 `eval_dialogue.ngram_repetition(t,3)`） | **单条回复内部**字符 3-gram 的重复占比 | 复读、车轱辘话、CoT 自我循环 |
| 12-gram 复用覆盖率（本报告引入） | **跨回复**的高频短语占了回复多少字符 | 模板套话、批量生成的同款回复 |

父 agent 的表用的是前者；而"同一批套话嵌在大量不同回复里"只有后者能看见。两者排序不同（§3）。

### 1.3 12-gram 覆盖率的定义（为什么它能回答"多少是套话"）

对某个源：

```
seq        = 该源全部「模型：回复」（span 口径）逐条去掉所有空白后的字符序列
窗口        = seq 上所有长度 12 的连续子串（回复很短时该回复的窗口数为 0）
count(g)   = 12-gram g 在**本源全部回复**中出现的次数（只在回复内部计数，不跨回复边界）
高频窗口    = count(g) > T
window 覆盖率 = 高频窗口数 / 窗口总数
union 字符覆盖率 = 「至少被一个高频窗口覆盖」的字符数 / 总字符数      ← 本报告表 1 用的就是这个
```

**为什么它能回答"这段文本有多少是套话"**：

- 一句话如果是在逐字复用一个模板，那么它上面**每一个** 12-gram 都会在其他回复里重复出现，于是它的字符全部落入"高频窗口"；
  一段原创的、上下文特定的话，其 12-gram 只出现一两次，不计入。**指标的分子就是"由复用短语构成的字符"，分母是"全部回复字符"**。
- 选 12 而不是 3~4：中文里 3-gram 的自然共现率极高（"的时"、"了一个"），阈值再高也压不住，会淹没信号；
  12 字≈一个短句片段，跨文档重复 20 次以上基本只有模板能做到。
- 选**并集**（而不是"高频窗口数占比"）是为了让数字有直接的物理含义：`0.96` = **这条源 96% 的回复字符来自出现 >20 次的话术**。
- **阈值 T 必须标定**（§2）：这不是一个"越大越脏"的任意指标，它有已知答案的可加性——§2.2 的注入实验里，覆盖率与"注入字符占比"**几乎逐点相等**。

### 1.4 计数实现与自证

- 12-gram 用 64 位多项式滚动哈希；计数用**固定槽位表**（2^29 槽 × uint16 = 1 GiB，模拟 NDB 的 hash%M 形态），
  分块 `sort + unique + 计数`，流式两遍（建表 / 查表+统计），绝不整体载入。
- **对照验证**：同一份数据上"固定槽位表"vs"精确 dict 计数"：`glm`（928,194 窗口、279,346 个不同 12-gram）
  两者各 T 的覆盖率差 ≤ 0.001（T=1: 0.8996 vs 0.8994；T=20: 0.0087 vs 0.0086）。槽位缩到 2^20 时 T=1 会被碰撞抬高 5 个百分点，
  所以 2^29 是必需的最小档（§2.3）。

### 1.5 抽样纪律

- **主结论全部来自全量扫描**（不用抽样，天然没有前缀偏差）。全库一遍约 45–75 s，内存 O(chunk)。
- 为了与父 agent 的抽样口径对齐，另做了**随机偏移抽样**（seek 到随机字节位置 → 跳过半行 → 取 128 KB）验证：
  `deepseek` rep3 全量 0.3828 / 随机抽样 0.3801 / **前缀抽样 0.3822**；`multi_turn` 0.0549 / 0.0543 / 0.0547；
  `qwen3` 0.3245 / 0.3257 / 0.3243；`zhihu` 0.0666 / 0.0662 / 0.0680。
  ⇒ 这几份文件内部是同质的，**前缀抽样本次没有偏差**（比值 0.974–1.004），但历史事故提醒不能依赖这一点。

| 对照 | T=1 | T=5 | T=20 | T=100 |

抽样为 200 次随机 seek × 128 KB（`multi_turn` 样本 ≈ 19.5% 的窗口）。

## 5. 清洗阈值建议

**规则定义（保证单调可解释）**：对每个 block，取其全部 `模型：` 回复（span 口径），计算

```
cov(block) = （至少在 1 个 count>T 的 12-gram 窗口里的字符数） / （回复去空白后总字符数）
若 block 没有 模型： 回复 → 不评估（保留）
丢弃条件：cov(block) > X
```

单调性：`T` 越大高频集合越小 ⇒ `cov` 单调不增；`X` 越大丢得越少。两者都可解释、无歧义。

### 表 7 轮间承接性：真实相邻 vs 打乱顺序（8-gram Jaccard）

相邻两条回复（去空白后）的字符 8-gram Jaccard = |A∩B| / |A∪B|；
对照 1 = 同一 block 内把回复顺序随机打乱 5 次后重算"相邻对"均值；对照 2 = 同 block 内任意两两配对的均值。

| 源 | 相邻对 Jaccard 均值 | 打乱后 Δ 中位 | 真实>打乱 的 block 占比 | 任意配对 Jaccard 均值 |
|---|---:|---:|---:|---:|
| `muice` | 0.0078 | 0.0000 | 5.4% | 0.0037 |
| `multi_turn` | 0.0066 | 0.0000 | 26.3% | **0.0066** |
| `kdconv` | 0.0007 | 0.0000 | 5.4% | 0.0015 |
| `lccc` | 0.0004 | 0.0000 | 0.3% | 0.0006 |
| `glm` | 0.0001 | 0.0000 | 0.3% | 0.0004 |

**读法**：`multi_turn` 的相邻对 0.0066 与"任意配对"0.0066 **完全相等** ⇒ 它的相邻轮并不比随便挑两轮更像，
所谓承接性只是"整源共享同一批模板句"的副产品。所有源的"真实 vs 打乱"Δ 中位数都是 **0.0000**，
即**打乱轮序不改变指标**——这正是要检验的零假设：**轮与轮之间没有可测的（8-gram 级）依赖**。

### 结论（回答父 agent 的问题）

- **"有逻辑的多轮"占比很小**：按 block 计 27.4% 有 ≥2 轮，但其中一半以上是 `multi_turn`（模板 + 无承接性）；
  按回复字符计 **≈90.5% 是单轮 QA 碎片**。
- **剩下的多轮部分也没有承接性**：`glm`/`kdconv`/`lccc`/`muice` 的相邻轮 8-gram Jaccard 都在 0.001 以下，
  且打乱顺序后不变。语料里的"多轮"是**离散轮次的拼接**，不是"轮与轮有逻辑依赖"的对话。
- 用户"模型会识字但没学会对话逻辑"的判断，**在语料侧得到支持**：语料本身几乎没有"逻辑多轮"可学。
  但注意证据强度：8-gram 是**表层代理**，它证明"没有逐字承接"，不能证明"没有语义依赖"（§9）。

### 打乱顺序的补充说明

恰好 2 轮的 block（如 `lccc` 的 52,250 个）打乱后相邻对集合不变，Δ 恒为 0，因此承接性对照只在 ≥3 轮的 block 上有效
（`multi_turn` 100,000 全在 ≥4 轮；`glm` 12,369 个 ≥4 轮；`lccc` 3,984；`kdconv` 1,872；`muice` 40）。

## 8. 附带发现（超出本次任务，但影响训练）

### 8.1 ★ `prepare.py` 把 `<eos>` 插在回答第一行之后（P0）

`annotate_replies` 只处理"以 `用户：`/`模型：` 开头的行"，续行原样保留。对多行回答的源：

```
原始：用户：能否提供...?\n模型：<think>\n好的,用户希望得到...(整段 CoT)
标注："A：能否提供...?"\n"B：<think>"<eos>\n好的,用户希望得到...(整段 CoT)
                              ^^^^^^ 终止符在这里
```

| 源 | 回复数 | 多行回复占比 | 首行是 `<think>` | **strict 字符 / span 字符** | 终止符位置中位数 |
|---|---:|---:|---:|---:|---:|
| `deepseek_r1` | 109,999 | **100.0%** | **100.0%** | 769,993 / 235,389,791 = **0.33%** | 0.38% |
| `qwen3_235b` | 109,999 | 97.2% | 0% | 6,701,552 / 112,876,114 = **5.9%** | 6.5% |
| `gsm8k_cot` | 7,473 | 100.0% | 0% | 89,676 / 1,858,545 = **4.8%** | 5.4% |
| `code_alpaca` | 14,909 | 13.8% | 0% | 82.7% | 10.8% |
| `coig_code` | 1,220 | 39.9% | 0% | 60.2% | 15.8% |
| `coig_other` | 9,856 | 34.4% | 0% | 60.1% | 23.1% |
| `glm`/`multi_turn`/`lccc`/`kdconv`/`zhihu`/`dailychat` | — | **≈0%**（zhihu 0.2%、其余 0%，基本无此问题） | | 100% | — |

后果：

- 旧口径（`use_loss_masking=true`，只对含 `<eos>/<cont>` 的行算 loss）下，`deepseek` 每条 block 只有
  `"B：<think>"<eos>` 这一行产生梯度（约 10 个 token），它 27.3% 的语料（235 M 字符）**梯度密度 ≈ 0.33%**。
  这是"88% 语料不产生梯度"背后**最大的一块**（AGENTS §6 只说了 c4/wiki 没有终止符）。
- 新口径（masking=false）下虽然全 token 都算 loss，但仍在教模型"`<think>` 之后就 EOS"、
  "第一句说完就 EOS"，续行则成了"EOS 之后的自由文本"。这与"回答答一半就停 / 不会对话逻辑"高度吻合。
- **这也解释了父 agent 的抽样为什么"几乎抽不到回复"**：`deepseek/qwen3` 的 strict 回复分别只有 7 字 / 61 字，
  而它们 96–99.7% 的字符在续行里。

**建议（未执行，只读任务）**：`annotate_replies` 应按 span 找回复边界（到下一个 `用户：`/`模型：` 行为止），
把 `<eos>/<cont>` 插在 span 末尾；并对 `模型：` 后的续行做同样的说话人/引号处理。这是一行级改动 + 已构建产物需重建。

> 相关（另一会话的模型侧报告 `analysis/turn_taking_v2.md`）：模型在 step 61000 上其实**学会了**"该 eos 还是 cont"这一层，
> 主要靠"回复里有没有问号"这条表层线索。与本节的发现互补：**语料侧的标注位置本身是错的**，
> 模型学到的是"第一行末尾该不该停"，而不是"整段回答说完了没有"。两者叠加是"答一半就停"的候选机制——
> 但这条因果链是**推断**，要修好标注重训才能验证。

### 8.3 四大名著是 CRLF（我第一遍扫描因此少算了 14,351 个 block）

`prepare.py` 用文本模式读（universal newlines，`\r\n`→`\n`），所以它切出 2,654/1,566/6,824/3,311 个 block；
我第一版用二进制读、按 `\n\n` 切，于是每本都只有 1 个 block，总数少 14,351、字符少 117,451。
**任何字节级工具（包括以后写的审计脚本）都必须先归一换行**，否则会静默得出错误结论。

## 9. 证据强度与不确定性

**实测（全量、可复现、有自证）**

- block 数 / 字符数 / 精确重复 / rep3 分布：26 个 txt **全量扫描**；block 与 manifest_v2 逐文件对账一致（差 4 block 的 `mix_tables` 已定位）。
- 12-gram 覆盖率：每源**两遍全量扫描**；固定槽位表与精确计数在 `glm` 上差 ≤0.001；合成对照（纯重复、注入扫描）给出已知答案。
- 轮数分布、相邻/打乱 Jaccard：**全量**。
- 高频 12-gram 的"全库精确次数"：全量 `str.count`（不是外推）。
- `<eos>` 位置：全量统计 + 直接调用 `prepare.py::annotate_replies` 复现了标注结果。
- 抽样纪律对照：4 个源上"全量 / 随机偏移 / 前缀"三方一致（0.974–1.004）。

**外推 / 有不确定性**

1. **12-gram 哈希碰撞**：2^29 槽、最大源 250 M 窗口，负载 ≈0.47；按泊松估计，罕见窗口被碰撞抬到 >5 的概率 ≈5e-5，
   对 T≥20 可忽略。但**只在 `dailychat`/`glm` 上直接验证过表 vs 精确**，250 M 窗口的源没有精确对照（内存不允许）。
2. **"套话"是代理**：覆盖率度量的是"复用的字符"，不含语义——高度专业但重复的文本（公式、代码、表格）也会被判脏
   （`qwen3`/`deepseek` 的高频片段就是 markdown 横线）。**不能用它一刀切判断"内容无价值"。**
3. **阈值 X 是判断，不是推导**：没有做"丢多少 → 下游 loss 降多少"的配对实验（那需要一个新 run）。
   本报告的 X 建议基于指标标定 + 代价表，**证据强度弱于 §2 的指标自证**。建议按 AGENTS §5.1 用
   `ckpt_paired_eval.py` 在同一 checkpoint 上做"清洗后子集 vs 原始"的配对 CE 验证。
4. **轮间承接性是表层代理**：8-gram Jaccard = 0 只证明"没有逐字承接"；语义依赖（同话题、追问-回答的语用关系）
   需要人工/模型判定。打乱对照的零结果在 `multi_turn` 上是干净的（n=100,000），但 `kdconv` 只有 1,872 个 ≥3 轮 block。
5. **`multi_turn` 的 96.4% 是"该源内部"的复用**。跨源复用（例如 `multi_turn` 与 `zhihu_kol` 共享套话）本次**没有**做全局表，
   所以 0.51% 的 `zhihu_kol` 是"源内干净"；若模板跨源流动，全局口径会略高（对 `zhihu_kol` 的定向抽查显示为 0，风险低）。
6. **`<eos>` 位置的下游影响未做实验**：机制清楚、样例可复现，但"它导致答一半就停"是**推断**，不是实测的因果。
