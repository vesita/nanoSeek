## 2. val 泄漏量化 [实测]

「泄漏」的定义：某个 val block 的**归一化文本**在 train 集合（全部 25 源）中出现过。train 侧只保留 digest 集合（流式，约 1.57M 条 16 字节键），没有把 2.2G 文本读进内存。

### 2.1 总量

| 指标 | 值 | 占分母 |
|---|---|---|
| val block 泄漏（归一化） | **1,315** | 1,315/15,818 = **8.31%** |
| val block 泄漏（精确） | 746 | 746/15,818 = 4.72% |
| 反向：train block 也出现在 val | 14,686 | 14,686/1,567,037 = **0.94%** |
| val token 泄漏（token 加权，val loss 的真实口径） | 117,891 | 117,891/9,417,945 = **1.252%** |
| val 内部自重复（val block 之间重复） | 106 | 0.67% |

⚠ **「对话」两套定义的差别很大，报告时必须写清用哪套**：

口径选择直接决定结论的量级 → 主结论用内容口径（1.79% / 0.39% token），文件名口径作为上界。

### 2.3 泄漏的**结构**：为什么是 8.31% 而不是 ~1%

两种机制，第二种是主因：

1. **高重数块**：单个 val block 的 train 副本数（`ndup`）分布极度偏斜 —— 1,017 个 val block 只有 1 个副本，另有一批有 300~1,007 个副本。按「源内二项切分」模型（k 个副本、p=0.01）理论期望只有 **151.7** 个泄漏 val block，实测 **1,315**（8.7 倍）。
2. **跨源重复（主因）**：**46,217 个归一化文本出现在 >1 个源**，涉及 **95,968 个 block**（COIG 家族之间互相重复最严重）。`split_one_source` 对**每个源独立 shuffle + 取前 1%** ⇒ 跨源重复的两份副本被独立分到两边的概率，比同一源内高约两个数量级。这正好解释了 8.7 倍的缺口。
   跨源矩阵 top：`coig_other ← coig_cqia` 222，`coig_cqia ← coig_other` 219，`code_alpaca ← code_alpaca` 192，`coig_wiki ← coig_cqia` 187 …

⇒ **对清洗设计的直接含义（[推断]，机制清晰）：只做「源内去重」不够，必须全局（至少跨 COIG 家族）去重后再切分。**

## 3. 配对 CE：泄漏 block vs 匹配对照 [实测]

### 3.1 口径（必须先说清）

- **模型**：`ckpt_step_61000.pt`，75.15M 参数，char-level，`block_size=256`，`eos_token_id=128`，`use_loss_masking=false`（step 61000 处于全量语料段），`use_mtp=false`、`use_aux_free_balance=true`。
- **CE 定义**：纯 token 级交叉熵、对一条 block 内**所有目标位置**取均值（token 加权），与 `estimate_loss` 的 token 加权同口径。
  - 自检 A：等长 batch 上，我的 CE 与模型自己返回的 `loss` **差值 0.0**（`{'model_loss': 0.55761826, 'my_ce': 0.55761826, 'abs_gap': 0.0}`）——aux-free MoE 下模型 loss 就是纯 CE。
  - 自检 B：编码器与 `prepare.encode_to_bin` 在已知样本上**逐 token 相同**。
  - 自检 C：单条 block 的 CE 与 batch 组成无关（同一 block 单独跑 / 与 16~256 token 的同伴混批，最大差 1.2e-06）。
- **固定标注口径**：两组都调用 `annotate_replies(block, ab_rate=1.0, quote_rate=1.0)`（恒 `A：/B：` + 恒引号）。
  **这**不是**逐位复现训练时的随机标注**（构建时是 `ab_rate=0.7 / quote_rate=0.8` 随机抽）——但该固定组合正是训练时约 **56%** 的 block 实际抽到的组合，所以泄漏项仍有充分的「同格式」匹配机会。这一点是本实验的**已知口径代价**。
- **★ `router_bias` 陷阱**：`model/mlp.py:134` 在**每次 forward**里就地对 `router_bias` 做 `sub_()`，**不看 `.training` / `no_grad`**。也就是说 eval 本身会漂移路由。我在每次 forward 前把 12 个 `router_bias` buffer 全部还原（快照），否则先评的那一组和第二组不可比、结果依赖求值顺序。`scripts/ckpt_paired_eval.py` 与 `estimate_loss` 都没有做这件事（这是项目侧一个独立的隐患，见 §5）。
- **配对设计**：对每个泄漏 block，从**同一个源、同一个 token 长度**的未泄漏 block 里**均匀随机**取一个做对照；两组长度分布因此完全一致（下表 `len a/len b` 与 `exact` 列）。
- **置换零假设（必须有，且真的救了命）**：把 `leak` 标签在池内随机重排 200 次，走**完全相同**的配对 + CE 流程，得到 Δ 的零分布。

### 3.2 主结果

| arm | n | Δ (nats) | se | t | 零假设 mean±sd | 置换 p |
|---|---|---|---|---|---|---|
| **A 对话源，同源 + 同 token 长度（主结果）** | 425 | **−0.083** | 0.067 | −1.24 | −0.001 ± 0.024 | <0.005 |
| A 对话源，同源，长度差 ≤2 | 476 | −0.105 | 0.065 | −1.61 | −0.006 ± 0.023 | <0.005 |
| A 对话源，同源，长度差 ≤8 | 501 | −0.058 | 0.061 | −0.95 | −0.005 ± 0.024 | 0.040 |
| A 对话源，**跨源** + 同长度 | 1,189 | **+0.444** | 0.053 | +8.35 | −0.009 ± 0.040 | <0.005 |
| B 严格对话，同源 + 同长度 | 28 | +0.342 | 0.199 | +1.72 | +0.002 ± 0.064 | <0.005 |
| B 严格对话，同源，长度差 ≤8 | 54 | +0.545 | 0.122 | +4.47 | −0.009 ± 0.058 | <0.005 |
| **对照 C1：val 对话源随机对半分，跨源 + 同长度** | 200 | **+0.068** | 0.109 | +0.62 | −0.008 ± 0.110 | 0.535 |
| **对照 C2：val 对话源随机对半分，同源 + 同长度** | 178 | **−0.034** | 0.069 | −0.49 | −0.002 ± 0.058 | 0.545 |

**两个空白对照都通过**：Δ 落在零分布内（p=0.54 / 0.55），证明这条流水线在「没有差异」时不会报出差异。

**主结果的读法**：Δ = CE(泄漏) − CE(对照)。
- 同源 + 同长度：Δ = −0.083，方向与「泄漏让模型占便宜」一致（泄漏块更**容易**），但 **t=−1.24，单独不显著**；95% CI = [−0.214, +0.048]。
- 跨源 + 同长度：Δ = **+0.444**，即泄漏块**更难**。**这不是记忆效应，是来源构成**（见 §3.3）—— 千万别把它读成「泄漏让 val 偏悲观」。

为什么来源差异这么大？因为**各源的 CE 水平差 8 倍以上**（同一次全池测量）：

| 源 | 池均 CE | 源 | 池均 CE |
|---|---|---|---|
| multi_turn_dialogue | **0.461** | coig_wiki | 2.924 |

### 3.4 曝光量—CE 关系（泄漏强度的内部对照）

只看泄漏块，按 train 副本数 `n_twin` 分桶（**同一批固定标注 + 同一模型**）：

| n_twin（train 副本数） | block 数 | 平均 CE | 平均 token 长度 |
|---|---|---|---|
| 1 | 986 | **3.752** | 79.6 |
| 2–5 | 69 | 2.029 | 64.2 |
| 6–50 | 68 | 1.501 | 47.9 |
| 51–200 | 44 | 0.776 | 29.8 |
| ≥201 | 61 | 1.042 | 20.8 |

Spearman(ρ) 池内 = **−0.428**；分源：coig_wiki −0.474、code_alpaca −0.171、coig_cqia +0.030、coig_other +0.105。

[推断] 方向是「曝光越多越容易」，且长度混杂是**反方向**的（高曝光块更短，而短的本来更难）——所以这个信号不是长度造成的。但它仍然与**内容类型**混杂（高重数块多是模板/样板片段，本身就更好猜），**不能当成纯记忆效应的证明**。

### 3.5 对历史 val loss 的影响：直接估计 + 模型无关上界

val loss 是 token 加权，所以只有 **1.252%** 的 token 受影响。

- **直接估计**（把 §3.3 的逐源 Δ 乘上该源的泄漏 token 占比再加总）：
  `Σ_s (leaked_tokens_s / 9,417,945) × (−Δ_s) = −0.00018 nats`，即 **≈ 0 ± 0.005 nats**（符号都不确定）。
- **激进外推**（把测得的最大单项 |Δ| = 0.358 应用到**全部**泄漏 token）：`0.01252 × 0.358 = 0.0045 nats`。
- **模型无关上界**（假设这 1.25% 的 token 被**完美记忆**，CE 降到 0，而对照 CE≈3.29）：`0.01252 × 3.29 = 0.041 nats`。
- 对照尺度：`AGENTS.md` §5.1 记录的单次 val 测量噪声 **σ≈0.087 nats**，每千步真实进步 ≈0.010 nats。

⇒ [实测+推断] **即使按最极端的「完美记忆」假设，泄漏也只能把历史 val loss 压低 ~0.04 nats，不到一次 eval 噪声的一半；按实测效应则 ≈0.001 nats。** 历史 val 数字偏乐观的程度**不足以解释任何一次被观察到的下降或平台**。

## 4. 方法学警告：这条路上有 3 个「假 Δ」，全部由空白对照抓出来

初版流水线给出 C2 置换对照 Δ = **+0.886**（8σ）—— 一个纯属测量方法自身的假效应。根因是**配对器在等长桶内做了确定性选择**，而池顺序 = 文件顺序，于是「按长度配对」偷偷变成了「按来源配对」：

| 版本 | 等长桶内的隐含选择 | 造成的假 Δ |
|---|---|---|
| v1 | 从桶的**最小 pool 下标**开始向外走 | 对照 Δ = +0.80（伙伴全来自 code_alpaca，CE 0.78） |
| v2 | `list.pop()` 取桶的**最后一个** | 对照 Δ = −1.02（伙伴全来自 zhihu_kol，CE 3.50） |
| v3（最终） | 长度与桶内元素**都均匀随机** | 对照 Δ = +0.068 / −0.034，落在零分布内 ✓ |

**代价**：`AGENTS.md` §5.4「新测量函数先在已知答案的输入上跑一遍」在这里不是形式 —— 没有 C1/C2 这两个对照，本报告会得出**符号都反了**的结论。
**给后续 agent 的直接建议**：任何 train/val、泄漏、配比类对比，**必须**带一个「同一流程 + 打乱标签」的置换零分布，并把 Δ 报成相对零分布的位置，而不是裸报一个 Δ。

## 5. 结论、限制、建议

### 5.1 回答任务的四问

1. **val 泄漏率**：整体 **8.31% 的 val block（1,315/15,818）/ 1.25% 的 val token**；严格对话 **1.79% block / 0.39% token**；精确（不归一化）口径 4.72% block。[实测，切分逐字节验证]
2. **是否足以让历史 val 偏乐观**：**不足以**。实测效应 ≈0 ± 0.005 nats；模型无关上界 0.041 nats ≪ σ_eval 0.087 nats。但泄漏**确实存在**，是有效性缺陷（对生成质量 / rep-n / NDB 检索这类对记忆敏感的量，1.25% 的逐字节重叠是实打实的 bug，即使 loss 上看不出来）。[实测+推断]
3. **配对 CE 的 Δ**：同源+同长度的主结果 **Δ = −0.083 ± 0.067 nats（n=425）**，方向符合记忆效应但不显著；效应集中在 `code_alpaca`（−0.358 ± 0.037，n=112，p<0.005），`coig_wiki` 与 `coig_other` 未测出（−0.043 ± 0.097 / +0.292 ± 0.278）。**证据强度：单 checkpoint、单 seed、N 有限，只能写「未测出显著的整体效应，且小到不影响历史 val」**，不能写「证明泄漏无害」。[实测]
4. **是否支持「清洗必须在切分前去重」**：**支持** [实测]。三条具体依据：
   (a) 1.25% 的 val token 与 train 逐字节（去空白）相同，单块最多 1,007 个 train 副本；
   (b) 泄漏集中在 COIG/code_alpaca，正是「模板化、高重数」的那部分；
   (c) **主因是跨源重复**：46,217 个文本 / 95,968 个 block 跨源重复，而「源内独立切分」让跨源副本落到两边的概率高两个数量级 —— **只做源内去重会漏掉大部分泄漏**。
   → 去重必须在切分**之前**做，**且是全局（跨源）去重**。理由写成「正确性 / 可复现的 val 语义」，不要写成「不改数值会差很多」。

### 5.2 本报告的限制（写结论时必须带上）

1. **只量了逐字节（去空白后）重复**。近重复（模板变体、共享前缀、改写）**没有量**，因此真实的 train/val 重叠 **≥ 本报告的 1.25%**，对应的 loss 影响也可能更大。这是本报告最主要的开口。
2. **固定标注口径**：两组都用 `ab_rate=1.0, quote_rate=1.0`，不是逐位复现训练时的随机标注（见 §3.1）。这削弱了对「格式级记忆」的检验能力。
3. **主结果 n 只有 425 对**：同源 + 同长度 + 需要有未泄漏对照，只有 425 个泄漏 block 满足；`coig_cqia`（占 val token 0.48%，99.3% 泄漏）只有 4 个未泄漏对照，**被排除在配对之外**，其泄漏效应完全未测。
4. **单 checkpoint、单 seed**；`ckpt_step_61000` 处于 `use_loss_masking=false` 段，与 ≤22000 的旧口径不可比（`AGENTS.md` §5.6）。
5. `router_bias` 我在测量时冻结了；训练/`estimate_loss` 未冻结，所以我的绝对 CE 与 `results.csv` 的 val/loss 不是同一个数（量级一致：池均 2.375 vs 该步 val 2.4562）。

### 5.3 顺带发现的、与本任务无关但值得记一笔的问题

- **`model/mlp.py:134` 在 eval 时也会改写 `router_bias`**（`use_aux_free_balance=true`，`balance_factor=0.001`/次）。`estimate_loss` 每次 eval 200 个 batch × 12 层都会推动路由偏置；`scripts/ckpt_paired_eval.py` 同样。量级上每次 0.001 很小，但它是**累积的、改变模型状态的评估**，且让 eval 结果依赖求值顺序。建议在 eval 前冻结、eval 后恢复（本报告的做法），或在 `mlp.py` 里把更新门到 `self.training`。[实测：代码路径已确认，数值影响未量化]
- **`data/chinese/mix_tables.txt` 是 v2 之后加入的**：今天直接重跑 `prepare.py` 会得到 26 个源、与 v2 不可比。任何「重建 v2」都必须按 manifest 的 25 文件清单跑。
